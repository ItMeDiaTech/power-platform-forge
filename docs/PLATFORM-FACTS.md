# Platform facts

What this plugin assumes about Claude Code and Microsoft's platforms, with the evidence for each assumption. Every entry is dated. Entries marked **live** were observed on a real run; entries marked **documented** come from the vendor's documentation, read on the date shown. Nothing here names a tenant, a person or an item: the repository is public.

Re-check any entry older than 30 days before relying on it in new code.

## Claude Code hooks, plugins and MCP (2026-10-26, Claude Code 2.1.310, Windows 10 with Git Bash)

Source of the live entries: a throwaway plugin loaded with `claude -p --plugin-dir <spike> --output-format stream-json --verbose --include-hook-events --debug=hooks,mcp`.

| # | Fact | Evidence |
|---|---|---|
| 1 | A PreToolUse hook that prints `permissionDecision: "allow"` plus a top-level `systemMessage` lets the command run and shows the message to the user as a notice-level line, `PreToolUse:<Tool> says: <message>`. The model does not see it. | live (stream-json `system/informational`, level `notice`); interactive display documented in [hooks](https://code.claude.com/docs/en/hooks.md) |
| 2 | `permissionDecision: "ask"` with a `permissionDecisionReason` asks the user, with the reason shown in the prompt. In `-p` runs nobody can answer, so the call is denied and the reason is returned to the model. A hook `ask` also forces a prompt in auto mode. | live in `-p` (`permission_denied`, `decision_reason_type: hook`); prompt and auto-mode behaviour documented in [hooks](https://code.claude.com/docs/en/hooks.md) |
| 3 | With `"onFailure": "block"`, a hook whose script is missing blocks the call (Python exits 2 for a missing file, which also reads as a block). | live |
| 4 | With `"onFailure": "block"`, a hook that exceeds its `timeout` (seconds) blocks the call, and so does a hook that crashes with exit 1. Without `onFailure`, both would let the call through. `onFailure` needs Claude Code 2.1.295 or later. | live (debug log: `timed out; blocking`, `failed; blocking`); version from [hooks](https://code.claude.com/docs/en/hooks.md) |
| 5 | Hook stdin for Bash and PowerShell is `{session_id, transcript_path, cwd, prompt_id, permission_mode, effort, hook_event_name, tool_name, tool_input: {command, description, timeout?, run_in_background?}, tool_use_id}`. For an MCP tool, `tool_input` is the call's arguments and `mcp_server: {name: "plugin:<plugin>:<server>", source: "plugin"}` is added. SessionStart stdin is `{session_id, transcript_path, cwd, hook_event_name, source}`. | live |
| 6 | Hook processes and plugin MCP server processes receive `CLAUDE_PLUGIN_ROOT`, `CLAUDE_PLUGIN_DATA` and `CLAUDE_PROJECT_DIR` (native backslash paths). SessionStart also receives `CLAUDE_ENV_FILE`. Commands Claude runs through the Bash or PowerShell tool do not receive the plugin variables. A plain `export NAME=value` written to `CLAUDE_ENV_FILE` reached the PowerShell tool; on Windows a value containing `/` or `\` never does. | live (hook and MCP env, `CLAUDE_ENV_FILE` to PowerShell); Bash-tool absence and the path rule documented in [plugins reference](https://code.claude.com/docs/en/plugins-reference.md) and [hooks](https://code.claude.com/docs/en/hooks.md) |
| 7 | `${CLAUDE_PLUGIN_ROOT}` and `${CLAUDE_PLUGIN_DATA}` written in a plugin SKILL.md body are replaced with real paths (forward slashes) before the model reads it. | live |
| 8 | `/reload-plugins` prints `Reloaded: N plugins · N skills · N agents · N hooks · N plugin LSP servers` in a non-interactive run (the MCP server count is added in interactive sessions), plus an error count when a plugin failed to load. From Git Bash, pass it to `claude -p` with `MSYS_NO_PATHCONV=1`, or Git Bash rewrites the slash command into a file path. | live (`-p`); format documented in [plugin CLI reference](https://code.claude.com/docs/en/plugins/cli-reference.md) |
| 9 | A stdlib-only MCP server that answers `server/discover` with JSON-RPC `-32601` is reached on the 2025-11-25 handshake: Claude Code probes the 2026-07-28 revision first, then sends `initialize`, then `tools/list`. Tools are named `mcp__plugin_<plugin>_<server>__<tool>` and are deferred behind tool search. `${CLAUDE_PLUGIN_ROOT}` and `${CLAUDE_PLUGIN_DATA}` are substituted in `.mcp.json` `args` and `env`, and equally in an inline `mcpServers` object in `.claude-plugin/plugin.json` (live with the installed 0.2.0 release). A root `.mcp.json` is also read as a project-scope server when Claude Code runs inside the plugin's own repository, so this plugin declares its server inline. A PreToolUse matcher written as a regex on the tool name fires for the plugin's MCP tools. | live |
| 10 | An `if` rule holds exactly one permission rule. It matches subcommands of compound commands (`cd x && cmd`), ignores a leading `VAR=value`, and PowerShell rules accept a leading wildcard (`PowerShell(*-Thing*)`). When Claude Code cannot parse a command (for example `echo "$VAR"`), every `if`-filtered handler runs. The change-notice hook therefore uses one handler per matcher and no `if`, so each shell call spawns it exactly once. | live |
| 11 | Exec form (`command` plus `args`) needs a real `.exe` on Windows. A hook launched as `uv run --no-project --offline --python >=3.10 python -I -S <script>` costs about 160 to 370 ms per call on the development PC. `uv` skips Microsoft Store alias stubs when it looks for an interpreter. | live (timings); `.exe` rule documented in [hooks](https://code.claude.com/docs/en/hooks.md) |
| 12 | `claude plugin validate --strict` fails on any warning: a missing `version`, `description` or `author`, an unknown manifest key, a `CLAUDE.md` at the plugin root, or a marketplace entry whose version differs from `plugin.json`. It needs no credentials or network. With `"source": "./"` the repository root is the plugin root, so the gitignored root `CLAUDE.md` must not be present when validating; CI checks out only tracked files. | live; [manifest reference](https://code.claude.com/docs/en/plugins/manifest-reference.md) |
| 13 | Installs are cached per version under `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/`. The version is `plugin.json`'s `version`; pushing commits without bumping it leaves users on the cached copy. `claude plugin update <plugin>@<marketplace>` refreshes the marketplace and installs a newer version; `claude plugin marketplace update` alone only refreshes listings. A running session picks up the new version after `/reload-plugins`. | documented in [plugin loading](https://code.claude.com/docs/en/plugins/loading.md) and [install](https://code.claude.com/docs/en/plugins/install.md) |
| 14 | `CLAUDE_PLUGIN_DATA` is `~/.claude/plugins/data/<plugin>-<marketplace>/`, survives plugin updates, and is deleted when the plugin is uninstalled from its last scope unless `--keep-data` is passed. | documented in [plugin components](https://code.claude.com/docs/en/plugins/components.md) |
| 14a | A hook handler's `if` rule matches only its own tool name for file tools: `Edit(**/*.Report/definition/**/*.json)` fires for the Edit tool but never for Write, and `Write(...)` fires for Write (2026-10-26, Claude Code 2.1.310, Windows). A file-path rule therefore needs one handler per tool. `**/` is relative to the session's working directory (a file outside the project never matches); `//**/`, `//c/**/` and `~/**/` match absolute paths, so the plugin uses `//**/`. | live (headless spike with `--plugin-dir`, PostToolUse hook events) |

## Microsoft agent plugins' MCP tools (2026-10-26)

Used by the change-notice classifier to decide which Microsoft MCP calls read, change something locally, or change the tenant. Read from the plugins' published source and package metadata; nothing was installed or run.

| # | Fact | Evidence |
|---|---|---|
| 17 | `powerbi-authoring@fabric-collection` adds one stdio server, `powerbi-modeling-mcp` (`npx -y @microsoft/powerbi-modeling-mcp@latest --start`, 1.0.0), with 23 tools: 22 `*_operations` tools plus `accept_eula`. Each `*_operations` tool is multiplexed by an `operation` value inside `tool_input.request` (casing varies, so match case-insensitively and accept an unwrapped form). Reads are `Help`, `Get*`, `List*`, `Find`, `Test`, `CheckStatusOfRefreshWithAPI`, `ExportTMDL`, `ExportTMSL`, `Execute`, `Validate`, `Report`, `GetStatus`, `ListActive`; everything else changes the connected model. `database_operations` `DeployToFabric` publishes to a workspace; `ExportToTmdlFolder` and `ExportToBimFile` write local files and are reported to delete existing `definition/` files (powerbi-modeling-mcp issue #96). Edits made over a `ConnectFolder` connection stay in memory until exported. Tool names look like `mcp__plugin_powerbi-authoring_powerbi-modeling-mcp__measure_operations`. | documented: [skills-for-fabric](https://github.com/microsoft/skills-for-fabric), npm package tool metadata, [issue #96](https://github.com/microsoft/powerbi-modeling-mcp/issues/96) |
| 18 | `power-automate@power-platform-skills` adds `flowagent` (62 tools, every tool annotated) and `microsoft-learn` (3 read-only tools). FlowAgent tenant changes: `create_flow`, `update_flow`, `edit_flow` (no write when `dryRun` is true), `copy_flow`, `publish_flow`, `disable_flow`, `delete_flow`, `run_flow`, `cancel_run`, `resubmit_run`, `cancel_all_runs`, `pick_or_create_connection`, `fix_connection`, `delete_connection`, `smoke_test`, `run_desktop_flow`, `restore_backup`. Mutating tools refuse managed-solution flows unless `forceManaged` is true, and write backups under `.flowagent/backups` in the server's working directory. | documented: [power-platform-skills](https://github.com/microsoft/power-platform-skills) `plugins/power-automate` (server bundle read, not run) |
| 19 | Installing both Microsoft plugins adds about 88 MCP tools to a session (23 plus 65). With tool search on (the default), only their names load until a tool is needed. | derived from 17 and 18; tool search documented in [MCP](https://code.claude.com/docs/en/mcp.md) |

## Power Apps maker PowerShell module (2026-10-26, Microsoft.PowerApps.PowerShell 1.0.49, Windows PowerShell 5.1)

| # | Fact | Evidence |
|---|---|---|
| 20 | The module keeps its sign-in only in the PowerShell process that ran `Add-PowerAppsAccount`: `Get-JwtToken` acquires interactively when the in-process session is empty, and there is no token cache file. A fresh process per call would therefore open a sign-in window every time. | documented in the module source (PowerShell Gallery package 1.0.49, `AuthModule.psm1`) |
| 21 | `Set-PowerAppRoleAssignment`, `Restore-PowerAppVersion`, `Get-PowerApp` and `Get-PowerAppVersion` call the service without `-ThrowOnFailure`, so a refused call still exits 0; only the returned response object says it failed. | documented in the module source (1.0.49) |
| 22 | A Windows PowerShell 5.1 `NamedPipeServerStream` whose server disposes its only instance after each call leaves the name free for a moment: another process created a pipe of the same name in that gap within seconds (independent review, 2026-10-26). ppx's window therefore creates its next instance before answering (two instances at most), so the name is never free, and the client opens the pipe with `CreateFileW` (`SECURITY_SQOS_PRESENT \| SECURITY_IDENTIFICATION`) and checks `GetNamedPipeServerProcessId` against the recorded window before sending anything. Python's `open()` reports a busy pipe as `EINVAL` without the Windows code, which is why ppx calls `CreateFileW` itself. A synchronous read blocks `close()`; `CancelSynchronousIo` on the reading thread ends it. | live (ppx `tests/test_maker_session.py` against a real 5.1 process, 6 to 8 concurrent calls) |
| 23 | The execution policy governs script and configuration files, not commands: `Restricted` "permits individual commands, but doesn't allow scripts" and blocks module script files (`.psm1`). So the window's own code (sent with `-EncodedCommand`) runs under any policy, but the maker module loads only where the policy allows module scripts (`RemoteSigned`, the Windows default, does for Gallery-installed modules; `AllSigned` needs a trusted signature). | documented in [about_Execution_Policies](https://learn.microsoft.com/powershell/module/microsoft.powershell.core/about/about_execution_policies) (ms.date 2026-08-31) |
